## 1. 引言

### 1.1 编写目的

本文档旨在对 **SparkSQL 房源信息分析系统** 进行全面的可行性分析，从技术、经济、操作、数据、法律、进度等多个维度评估项目的可行性，识别潜在风险并提出应对措施，为项目决策提供依据。

### 1.2 项目背景

房地产市场数据庞大且分散，传统的关系型数据库在处理海量房源数据、多维度聚合分析时面临性能瓶颈。本系统利用 SparkSQL 的分布式计算能力，结合 Kafka 实时流处理，构建一套从数据采集、清洗、分析到结果输出的端到端房源信息分析平台。

### 1.3 系统目标

| 目标 | 描述 |
|------|------|
| 数据采集 | 从 CSV 文件批量导入原始房源数据，支持中文字段名自动映射 |
| 数据清洗 | 过滤无效数据、标准化字段类型、生成派生指标（单价、房龄等） |
| 多维分析 | 按面积区间、市区、建造年份、小区四个维度进行聚合统计 |
| 实时处理 | 通过 Kafka 实现特定条件房源数据的实时采集与增量更新 |
| 断点续跑 | 流处理链路支持进度持久化，重启后从断点继续 |

### 1.4 术语与缩写

| 术语/缩写 | 说明 |
|-----------|------|
| ODS | Operational Data Store，操作数据层，存储原始数据 |
| DWD | Data Warehouse Detail，数据仓库明细层，存储清洗后数据 |
| ADS | Application Data Service，应用数据服务层，存储分析结果 |
| SparkSQL | Apache Spark 的 SQL 模块，支持结构化数据处理 |
| checkid | 批次标识，用于区分不同批次的数据 |

### 2.2 性能可行性

#### 2.2.1 批处理链路

| 环节 | 计算引擎 | 预估性能 |
|------|----------|----------|
| CSV 读取 | Spark 单机/集群 | 10万行/秒级别（取决于集群规模） |
| 数据清洗 | SparkSQL | 内存计算，近线性扩展 |
| 面积区间分析 | SparkSQL (3 层 CTE) | 百万级数据秒级完成 |
| 市区维度分析 | SparkSQL (单层聚合) | 百万级数据秒级完成 |
| 年份区间分析 | SparkSQL (2 层 CTE + 正则) | 百万级数据 3-5 秒 |
| 小区维度分析 | SparkSQL (单层聚合) | 百万级数据秒级完成 |
| MySQL 写入 | JDBC batch write | 取决于网络和 MySQL 配置 |

#### 2.2.2 流处理链路

| 环节 | 处理方式 | 预估性能 |
|------|----------|----------|
| Producer 轮询 | 1秒间隔 | 无数据时几乎零开销 |
| Kafka 传输 | 异步发送，acks=all | 毫秒级延迟 |
| Consumer 消费 | Poll 100ms | 实时消费 |
| 内存聚合 | ConcurrentHashMap | O(1) 插入/更新 |
| 批量写入 MySQL | PreparedStatement batch | 批量事务，效率高 |

### 2.3 技术风险评估

| 风险项 | 风险等级 | 说明 | 应对措施 |
|--------|----------|------|----------|
| MySQL 成为瓶颈 | 🟡 中 | 所有 ADS 表写入同一 MySQL 实例 | 读写分离、结果表可考虑 Hive/ClickHouse |
| Spark 单机模式 | 🟡 中 | 当前 master("local[*]") 或未指定 master | 生产环境需提交到 YARN/K8s 集群 |
| JDBC Driver 过时 | 🟢 低 | `com.mysql.jdbc.Driver` 已废弃 | 升级为 `com.mysql.cj.jdbc.Driver` |
| 内存聚合 OOM | 🟡 中 | 小区数量过大时 Consumer 内存溢出 | 设置上限，超限时强制 flush |
| 无认证机制 | 🟠 高 | Kafka 无 SASL/SSL，MySQL 明文密码 | 生产环境需配置安全认证 |

## 4. 操作可行性分析

### 4.1 用户角色与操作流程

| 角色 | 操作 | 频率 | 复杂度 |
|------|------|------|--------|
| 数据管理员 | 上传新 CSV 文件到指定路径 | 按需 | 低 |
| 运维人员 | 依次执行 Write2Db → 各 Analysis 程序 | 按需 | 低 |
| 运维人员 | 启动 Producer + Consumer | 持续运行 | 低 |
| 业务分析人员 | 查询 ADS 结果表 | 按需 | 低（SQL 查询） |

### 4.2 操作流程

#### 4.2.1 批处理操作流程

```
1. 将 CSV 文件放置到 /home/master/sparkproject/wholedata.csv
2. 运行 Write2Db.scala → 自动完成数据导入 + 清洗
3. 按需运行分析程序:
   - AreaAnalysis.scala      → 面积区间分析
   - DistrictAnalysis.scala  → 市区维度分析
   - YearAnalysis.scala      → 建造年份分析
   - CommunityAnalysis.scala → 小区维度分析
4. 查询 MySQL 中的 ADS 结果表
```

#### 4.2.2 流处理操作流程

```
1. 确保 Kafka 集群正常运行
2. 启动 Consumer.java (先启动，等待消息)
3. 启动 Producer.java (开始轮询并发送)
4. 监控: Kafka 消息堆积、MySQL 写入成功率
5. 停止: 先停 Producer，确认无消息后停 Consumer
```

## 5. 数据可行性分析

### 5.1 数据来源

| 数据源 | 格式 | 规模 | 质量 |
|--------|------|------|------|
| wholedata.csv | CSV (UTF-8) | 取决于实际采集 | 含无效数据（空值、异常面积、异常年份） |

### 5.2 数据质量保障

| 质量问题 | 清洗规则 | 效果 |
|----------|----------|------|
| 市区为空 | `district IS NOT NULL` 过滤 | 过滤空值 |
| 小区名为空 | `community IS NOT NULL` 过滤 | 过滤空值 |
| 面积异常（≤0） | `area > 0` 过滤 | 过滤非正面积 |
| 价格异常（≤0） | `price > 0` 过滤 | 过滤非正价格 |
| 建造年份格式错误 | `build_year REGEXP '^[0-9]{4}$'` 过滤 | 仅保留四位数字年份 |
| 年份范围异常 | `build_year >= 1950 AND build_year <= 2020` (YearAnalysis) | 限定合理范围 |

### 5.3 数据量评估

| 表名 | 层 | 数据量级 | 增长模式 |
|------|-----|----------|----------|
| house_info_checkid | ODS | 与 CSV 行数 1:1 | 全量覆盖 / 增量追加 |
| house_info_clean_checkid | DWD | ≤ ODS 行数（过滤后） | 随 ODS 增长 |
| area_price_analysis | ADS | ~4 行/批次 (4个区间) | 固定行数 |
| district_house_price_analysis | ADS | ~N 行/批次 (N个市区) | 随市区数增长 |
| house_year_analysis | ADS | ~5 行/批次 (5个区间) | 固定行数 |
| community_price_analysis | ADS | ~M 行/批次 (M个小区) | 随小区数增长 |
| certain_analysis | ADS | ~M' 行 (海淀90-144㎡小区) | 随小区数增长 |
| kafka_producer_progress | 辅助 | 1 行 | 恒定 |

### 5.4 数据一致性

| 机制 | 实现方式 | 说明 |
|------|----------|------|
| 批次隔离 | checkid 字段 | 不同批次数据互不干扰 |
| 唯一约束 | uk_checkid_district_community | 防止同一小区重复记录 |
| 幂等写入 | INSERT ON DUPLICATE KEY UPDATE | 重复执行不产生脏数据 |
| 加权平均 | Consumer 端合并公式 | 保证多次更新的统计正确性 |

### 5.5 数据可行性结论

数据来源明确，清洗规则完备，数据模型设计合理（分层架构 + 批次隔离），一致性机制到位。数据层面 **完全可行**。

## 8. 风险分析与应对措施

### 8.1 风险矩阵

```
影响程度
  ▲
高│  ⑥       ①
  │
中│  ③  ⑤   ②
  │
低│      ④
  └──────────────────► 发生概率
     低    中    高
```

| 编号 | 风险项 | 概率 | 影响 | 等级 |
|------|--------|------|------|------|
| ① | MySQL 单点故障导致全系统不可用 | 低 | 高 | 🟡 中 |
| ② | 数据量增长超出 MySQL 承载能力 | 中 | 高 | 🟠 高 |
| ③ | Kafka 集群故障导致流链路中断 | 低 | 中 | 🟢 低 |
| ④ | CSV 数据格式变化导致导入失败 | 低 | 低 | 🟢 低 |
| ⑤ | Consumer 内存溢出 | 中 | 中 | 🟡 中 |
| ⑥ | 安全漏洞（明文密码、无认证） | 中 | 高 | 🟠 高 |

### 8.2 应对措施

| 风险 | 应对措施 | 实施难度 |
|------|----------|----------|
| ① MySQL 单点 | 配置 MySQL 主从复制 + 读写分离 | 中 |
| ② 数据量增长 | ① ADS 表按 pt_date 分区；② 历史数据归档；③ 评估迁移至 ClickHouse/Hive | 中-高 |
| ③ Kafka 中断 | Producer 轮询机制天然容忍 Kafka 短暂不可用（发送失败 → 下轮重试） | 低（已有） |
| ④ CSV 格式变化 | Write2Db 增加 Schema 校验 + 列数检查 | 低 |
| ⑤ Consumer OOM | 设置 communityStats 最大条目数，超限强制 flush | 低 |
| ⑥ 安全漏洞 | ① 密码移至配置文件/环境变量；② Kafka 启用 SASL/SSL；③ MySQL 限制访问 IP | 中 |
